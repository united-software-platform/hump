## Context

Мотивация — в `proposal.md` (раздел «Why»). Наблюдаемое состояние окружения на момент планирования:

- шлюз поднят одним сервисом `litellm` в `docker-compose.hump.yml`, базы данных рядом нет;
- `/health/readiness` отвечает `{"status": "healthy", "db": "Not connected"}`;
- `/ui/` отвечает `200` и отдаёт страницу входа, но авторизация завершается
  `Authentication Error, Not connected to DB!`;
- ключ доступа к API моделей ровно один — `LITELLM_MASTER_KEY` из `.env`, им пользуются все
  потребители;
- `LITELLM_SALT_KEY` в `.env.example` уже объявлен с пометкой «сейчас БД нет, значение про запас».

Ограничения окружения: `docker-compose.yml` принадлежит SDD kit'у и правке не подлежит — сервисы
продукта живут в `docker-compose.hump.yml`; в контейнере агента нет Docker, поэтому запуск
и проверка выполняются на хосте через цели `make` из белого списка host-runner'а.

## Goals / Non-Goals

**Goals:**

- Вход в панель выполняется и показывает маршруты, обращения и ключи.
- Состояние шлюза переживает `make hump-down` и последующий `make hump-up`.
- Системе-потребителю можно выдать собственный ключ и отозвать его, не трогая остальных.
- Проверка `make hump-check` отличает «база не подключена» от «шлюз не запущен».

**Non-Goals:**

- Панель не публикуется за пределы хоста и не получает TLS — это предмет отдельного решения
  о развёртывании.
- Права пользователей панели не разграничиваются: администратор один.
- Ключи провайдеров в базу не переносятся, `config/litellm.yaml` продолжает ссылаться
  на переменные окружения.
- Отчётность и алерты поверх собранных данных не строятся.

## Decisions

### Решение 1. PostgreSQL отдельным сервисом того же compose-файла

База поднимается сервисом в `docker-compose.hump.yml`, порт наружу не публикуется — к базе
обращается только шлюз по внутренней сети, как уже сделано для Ollama.

Альтернативы: внешняя база на хосте (отвергнуто — установка перестаёт быть воспроизводимой одной
целью `make hump-up`); SQLite (отвергнуто — LiteLLM рассчитывает на PostgreSQL, а миграции
и параллельный доступ на файловой базе ведут себя иначе).

### Решение 1а. Данные сервисов — в каталоге проекта, а не в томах Docker

Уточнение решения 1 по ходу применения, по запросу пользователя: данные базы и веса моделей лежат
в `data/postgres/` и `data/ollama-models/` внутри репозитория; именованные тома `postgres-data`
и `ollama-models` из compose-файла убраны.

Основание: содержимое видно и копируется обычными средствами, без `docker volume` и временных
контейнеров, — резервная копия и перенос проекта на другую машину становятся файловой операцией.

Следствия, которые пришлось закрыть отдельно:

- `data/` исключён из репозитория (`.gitignore`) — иначе в историю попадают гигабайты весов
  и файлы базы;
- каталоги создаёт `make init-dirs` заранее: каталог, созданный docker'ом под точку монтирования,
  принадлежит `root`, и работать с ним с хоста без `sudo` уже нельзя;
- у базы задан `PGDATA` в подкаталоге точки монтирования: `initdb` требует пустой каталог,
  а у смонтированного каталога хоста могут быть свои записи и права;
- `data/postgres/` принадлежит пользователю базы из образа (uid 999), а не владельцу репозитория —
  удаление каталога требует `sudo`, и это отражено в README.

Альтернатива — оставить именованные тома (отвергнуто пользователем): данные не видны рядом
с проектом, а резервное копирование требует отдельной процедуры с временным контейнером.

### Решение 2. Строка подключения собирается в `.env`, а не подставляется compose'ом

`DATABASE_URL` задаётся в `.env` целиком и попадает в контейнер через `env_file`, как уже сделано
для `OLLAMA_API_BASE`. Причина та же, что зафиксирована комментарием в compose-файле: подстановка
`${...}` берёт значение из окружения процесса, запустившего compose, и одноимённая переменная хоста
молча перекрыла бы значение из `.env`.

Логин, пароль и имя базы задаются отдельными переменными для сервиса базы; их значения и содержимое
`DATABASE_URL` должны совпадать — это место двойной правки, и оно называется прямо в README
и в комментарии `.env.example`.

### Решение 3. Готовность базы — условие запуска шлюза

Шлюз получает зависимость от сервиса базы с ожиданием её готовности (healthcheck базы), а не просто
порядок запуска: при старте шлюз выполняет миграции, и обращение к ещё не принимающей соединения
базе даёт отказ при первом же входе в панель.

Альтернатива — полагаться на `restart: unless-stopped` и перезапуск шлюза (отвергнуто: приводит
к циклу перезапусков, в логах которого настоящая причина теряется).

### Решение 4. Учётные данные панели задаются явно

В `.env.example` добавляются `UI_USERNAME` и `UI_PASSWORD`, а в README фиксируется, что до их
заполнения действует вход `admin` с паролем, равным `LITELLM_MASTER_KEY`. Явные переменные
предпочтительны: мастер-ключ — секрет уровня API, и вход в панель под ним делает компрометацию
панели компрометацией всего шлюза.

### Решение 5. Проверка получает отдельный шаг о базе

В `tools/litellm/check.sh` шаг готовности дополняется разбором поля `db` в ответе
`/health/readiness`: значение, отличное от подключённого состояния, даёт отказ шага с прежним кодом
возврата `1`. Коды возврата скрипта не меняются — иначе разойдётся уже описанный контракт
`0`/`1`/`2`.

### Решение 6. Порядок применения относительно `revise-readme`

Изменение применяется после `revise-readme`: тот вводит раздел о панели с текущим ограничением,
а это изменение заменяет ограничение рабочей инструкцией. Обратный порядок потребовал бы описывать
в README состояние, которое уже не действует.

## Risks / Trade-offs

- **Секреты базы добавляются к уже имеющимся секретам** → `.env` исключён из репозитория,
  в `.env.example` хранятся только заглушки; порт базы наружу не публикуется.
- **Том с данными базы растёт без ограничений: записи об обращениях копятся** → в задачи включён
  пункт зафиксировать в README, что том растёт, и назвать команду его очистки; автоматическая
  ротация в изменение не входит.
- **Появляется место двойной правки: переменные сервиса базы и строка `DATABASE_URL`** →
  расхождение проявляется отказом входа в панель; место называется в комментарии `.env.example`
  и в README, по образцу уже существующего расхождения между `config/litellm.yaml`
  и `ollama-pull`.
- **Миграции схемы выполняются образом шлюза при старте, и смена тега образа может их изменить** →
  в `.env` тег образа закрепляем осознанно, `latest` для шлюза с базой опаснее, чем без неё;
  пункт вынесен в задачи.
- **Потеря тома означает потерю выданных ключей** → резервное копирование в изменение не входит
  и названо в README как обязанность эксплуатации.

## Migration Plan

1. Заполнить новые переменные в `.env` по обновлённому `.env.example`.
2. `make hump-up` — поднимается база, шлюз выполняет миграции при старте.
3. `make hump-check` — подтверждает готовность шлюза и подключение базы.
4. Войти в панель и выдать ключи системам-потребителям; мастер-ключ остаётся административным.

Откат: `make hump-down`, возврат прежних версий `docker-compose.hump.yml`, `.env.example`
и `tools/litellm/check.sh`, `make hump-up`. Шлюз возвращается к работе без базы; том с данными
сохраняется и может быть удалён отдельно.
