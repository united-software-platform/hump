## Context

Мотивация — в `proposal.md`, раздел «Why». Ограничения, из которых исходит решение, заданы текущим
состоянием репозитория:

- Кода в проекте нет: это первый исполняемый компонент. Стека приложения (язык, зависимости,
  сборка) тоже пока нет.
- `docker-compose.yml`, `Makefile` и `tools/host-runner/runner.py` поставлены SDD kit'ом и записаны
  в `.sdd-kit-manifest.json` с контрольными суммами. Изменение любого из них расходится
  с манифестом и может быть перезаписано при обновлении kit'а.
- В контейнере агента нет ни `docker`, ни `make`. Белый список host-runner'а — `init`,
  `openspec-init`, `help`: новые цели `make` агент запускать не сможет без правки файла kit'а.
- Контейнер агента видит хост как `host.docker.internal` (задано в `extra_hosts`), и в нём
  есть `wget` — то есть проверить по HTTP уже поднятый сервис агент может.
- `.env` исключён из репозитория и подменяется внутри контейнера агента на пустой файл: секреты
  доезжают до сервисов через `env_file`/переменные окружения, а не через чтение файла агентом.
- Имена `ANTHROPIC_*` зарезервированы самим Claude Code: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`
  и `ANTHROPIC_BASE_URL` в окружении агента отключают claude.ai-логин и коннекторы организации.
  В `.env` они лежат ради облачного маршрута LiteLLM — и оттуда же через `env_file` попадали
  в окружение агента, пока оба compose-файла читали один файл.

Требования к поведению — в `specs/llm-gateway/spec.md`.

## Goals / Non-Goals

**Goals:**

- Поднять LiteLLM Proxy как отдельный сервис и получить рабочий OpenAI-совместимый вход.
- Настроить два маршрута — локальный (Ollama) и облачный — и убедиться, что оба отвечают.
- Сервисы продукта держать в отдельном compose-файле; файлы SDD kit'а править только точечно
  и по отдельному основанию.
- Сделать проверку воспроизводимой: одна команда, понятный код возврата.

**Non-Goals:**

- Собственная логика маршрутизации Hump (выбор модели по типу задачи, ретраи, учёт расхода) —
  это следующие изменения; здесь только базовый маршрут через LiteLLM.
- Поднятие Ollama контейнером и управление загрузкой моделей.
- Персистентность LiteLLM (БД, ключи виртуальных пользователей, UI администратора).
- Публикация сервиса наружу, TLS, доменные имена.

## Decisions

### Отдельный compose-файл вместо правки китовского

Сервис описывается в собственном compose-файле проекта (`docker-compose.hump.yml`), а не в
`docker-compose.yml` SDD kit'а.

Причина — манифест: китовский файл идёт с контрольной суммой, и правка в нём при обновлении kit'а
либо перезаписывается, либо требует ручного разрешения расхождения. Отдельный файл разводит
окружение агента и сервисы продукта: обновление kit'а их не касается.

Альтернативы:

- Править китовский `docker-compose.yml` — отклонено по причине выше.
- Compose override (`docker-compose.override.yml`) — подхватывается автоматически и незаметно
  меняет поведение штатных команд kit'а; явный отдельный файл предсказуемее.

Исключение из правила — точечная правка `docker-compose.yml` ради разведения env-файлов, см.
«Отдельный env-файл агента (`.env.claude`)». Сервисы продукта в китовский файл по-прежнему
не добавляются.

### Отдельный env-файл агента (`.env.claude`)

Окружение агента переведено с `.env` на отдельный файл `.env.claude`, содержащий только переменные
агента. В `.env` остаются переменные продукта Hump — среди них `ANTHROPIC_API_KEY`,
`ANTHROPIC_AUTH_TOKEN` и `ANTHROPIC_BASE_URL`, имена которых зарезервированы самим Claude Code:
их попадание в окружение агента отключает claude.ai-логин и коннекторы организации.

До разделения оба compose-файла читали один `.env` через `env_file`, и `ANTHROPIC_*` доезжали
до агента. Разнесение по файлам развязывает их: `docker-compose.hump.yml` (`litellm`) продолжает
читать `.env`, а `docker-compose.yml` (`claude`) — `.env.claude`.

Это точечная правка китовского `docker-compose.yml`: `env_file: .env` заменён на `.env.claude`,
а новый файл добавлен в маскировку `/dev/null`, чтобы его содержимое не было доступно агенту
в виде файла. Цель `init-env` в `Makefile` создаёт `.env.claude` из `.env.claude.example`,
а `.gitignore` исключает его наравне с `.env`.

Альтернатива — переименовать переменные продукта (например `LITELLM_ANTHROPIC_*`) — отклонена:
переименование меняет блок конфигурации продукта и создаёт расхождение между `.env`, `.env.example`
и `config/litellm.yaml`, тогда как разделение файлов оставляет переменные продукта как есть.

### LiteLLM Proxy как контейнер, без кода приложения

Используется образ `docker.litellm.ai/berriai/litellm:latest` с конфигурацией, примонтированной
внутрь, и запуском с ключом `--config`.

Это даёт работающий шлюз без единой строки кода приложения: на этом шаге в проекте ещё нет ни
Python-проекта, ни сборки, и заводить их только ради подключения прокси преждевременно.

Альтернатива — Python SDK LiteLLM внутри собственного сервиса Hump: отклонено на этом шаге,
потребовало бы сначала создать структуру приложения; решение отложено до появления собственной
логики маршрутизации.

> **Внимание:** тег `latest` не фиксирует версию. Воспроизводимость сборки на этом шаге принесена
> в жертву простоте старта; закрепление версии — отдельная задача, см. «Risks / Trade-offs».

### Ollama — сервис в составе окружения Hump

Ollama поднимается контейнером в том же compose-файле, что и шлюз; веса лежат в именованном томе,
а модель загружает разовый сервис `ollama-pull` при каждом `up`.

Первоначально решение было обратным — Ollama на хосте, адрес через `host.docker.internal`, — исходя
из того, что его ставят на хост ради GPU и общего кэша моделей. Проверка на живом окружении это
опровергла: на машине разработчика Ollama либо не установлен, либо слушает только `127.0.0.1`
и из контейнеров недоступен, а отказ выглядит как отказ шлюза. Окружение, поднимающееся одной
командой, оказалось важнее экономии на повторной загрузке весов.

Порт Ollama наружу не публикуется: к нему обращается только шлюз по внутренней сети compose.
Адрес остаётся в переменной `OLLAMA_API_BASE`, значение которой живёт в `.env`, поэтому маршрут
можно увести на Ollama хоста или на отдельную машину правкой `.env`; `extra_hosts` у шлюза
сохранён именно для этого варианта.

Работа идёт на процессоре: резервирование видеокарты требует NVIDIA Container Toolkit на хосте
и выходит за рамки шага.

Для маршрута используется префикс `ollama_chat/`, а не `ollama/`: он направляет запрос на
`/api/chat` Ollama, что рекомендовано документацией для чат-моделей.

### Адрес Ollama — только через `env_file`

Переменная `OLLAMA_API_BASE` передаётся шлюзу единственным способом — через `env_file: .env`.
Блока `environment:` с умолчанием `${OLLAMA_API_BASE:-http://ollama:11434}` в compose-файле нет.

Первоначально умолчание в `environment:` стояло: без значения LiteLLM молча берёт свой
`localhost:11434`, который внутри контейнера указывает на сам шлюз, и отказ маршрута выглядит
беспричинным. На живом окружении решение дало обратный эффект. Подстановка `${...}` берёт значение
сначала из окружения процесса, запустившего compose, и только потом из `.env`, а блок
`environment:` старше `env_file`. Одноимённая переменная, оставшаяся в окружении host-runner'а
от прежней редакции `.env`, перекрыла верное значение: шлюз ходил на `host.docker.internal:11434`,
тогда как `.env`, `.env.example` и `config/litellm.yaml` были настроены верно — расхождение
не видно ни в одном файле репозитория.

`env_file` такой подстановке не подвержен: значение берётся из файла и переменной хоста
не перекрывается. Цена решения — потеря умолчания: переменная в `.env` становится обязательной,
и незаполненное значение возвращает тот самый молчаливый `localhost:11434`. Риск удерживается
комментарием в `docker-compose.hump.yml` и строкой `OLLAMA_API_BASE` в `.env.example`,
откуда `.env` и создаётся.

Альтернатива — оставить умолчание под отдельным именем, не совпадающим с тем, что читает
LiteLLM, — отклонена: LiteLLM читает именно `OLLAMA_API_BASE`, и промежуточное имя потребовало бы
ещё одного слоя подстановки ради того же результата.

### Конфигурация: только имена переменных окружения

В `model_list` ключи задаются формой `os.environ/<ИМЯ>`, значения — в `.env`, который уже исключён
из репозитория. `LITELLM_MASTER_KEY` (ключ доступа к самому шлюзу, обязан начинаться с `sk-`)
и `LITELLM_SALT_KEY` передаются сервису так же.

Это прямо выполняет требование спецификации «Секреты вне репозитория»: файл конфигурации можно
коммитить, он не содержит значений.

### Проверка — скрипт репозитория, запускаемый и целью `make`

Проверка оформляется скриптом (`tools/litellm/check.sh`): HTTP-клиент выбирается из доступных —
`curl`, иначе `wget`, — поэтому скрипт работает и на хосте, и в контейнере агента.

Поверх скрипта добавлена цель `hump-check`: она читает `.env` на хосте и передаёт скрипту
мастер-ключ. Так агент запускает проверку, не получая секрет в своё окружение — `.env` скрыт
от него намеренно.

Цели управления (`hump-up`, `hump-down`, `hump-logs`, `hump-check`) внесены в `Makefile` и в белый
список host-runner'а: это правка файлов kit'а, но без неё агент не может ни поднять окружение,
ни диагностировать его. Цели не ждут терминала и завершаются сами — раннер однопоточный, и
процесс в режиме слежения блокировал бы его до таймаута.

Последовательность проверки соответствует двум уровням из спецификации:

1. `GET /health/liveliness` и `GET /health/readiness` — без авторизации, подтверждают, что процесс
   жив и готов;
2. `GET /health` с мастер-ключом — прогоняет реальный запрос по каждому настроенному маршруту
   и возвращает списки здоровых и нездоровых эндпоинтов;
3. `POST /v1/chat/completions` по одному разу на каждый маршрут — сквозная проверка того, что
   ответ доходит до клиента в ожидаемом формате.

Скрипт завершается ненулевым кодом, если хотя бы один настроенный маршрут не ответил.

## Risks / Trade-offs

- **Тег `latest` не воспроизводим**: обновление образа может изменить поведение шлюза без правок
  в репозитории. → Адрес образа и тег вынесены в переменные окружения; закрепление конкретной
  версии — отдельная задача после того, как связка подтвердит работоспособность.
- **Проверка зависит от внешних предусловий**: без действующего ключа провайдера и без загруженных
  весов модели проверка упадёт не из-за ошибки конфигурации. → Скрипт различает уровни
  (живость/готовность отдельно от маршрутов) и называет конкретный неответивший маршрут.
- **Веса модели занимают место на диске**: первый запуск скачивает их в том `ollama-models`. →
  Модель выбрана небольшой; при нехватке места `up` заполнит диск, поэтому перед первым запуском
  свободное место проверяется.
- **Агент не может поднять сервис напрямую**: в его контейнере нет Docker. → Управление идёт
  целями `make` через host-runner (`hump-up`, `hump-down`, `hump-logs`, `hump-check`), для чего
  цели добавлены в `Makefile` и в белый список `tools/host-runner/runner.py`. Оба файла
  принадлежат kit'у и расходятся с его манифестом — осознанная плата за то, чтобы агент управлял
  окружением сам. Изменение белого списка требует перезапуска раннера на хосте.
- **Мастер-ключ не попадает в окружение агента**: цель `hump-check` читает `.env` на хосте, а сам
  файл от агента скрыт монтированием `/dev/null` — так проверка работает, не раскрывая секрет.
- **Мастер-ключ один на весь шлюз**: разграничения прав между системами-потребителями нет. →
  Приемлемо для локального запуска; виртуальные ключи LiteLLM требуют БД и выходят за рамки шага.
- **Переменные агента читаются из `.env.claude`**: значение, добавленное пользователем в `.env`
  ради агента, до него не доедет. → Раздел запуска в `README.md` называет оба файла и их назначение;
  комментарий в `docker-compose.yml` повторяет причину разделения.
- **Порт 4000 может быть занят** другим сервисом на хосте. → Порт публикации вынесен в переменную
  окружения.
- **`OLLAMA_API_BASE` без значения в `.env`**: умолчания на уровне compose больше нет, и LiteLLM
  молча берёт `localhost:11434` — сам контейнер шлюза. → Переменная есть в `.env.example`, из
  которого создаётся `.env`, а `hump-check` называет в ошибке маршрута фактический адрес.

## Migration Plan

Миграция для существующего окружения: создать `.env.claude` из текущего `.env`, исключив
переменные продукта, и пересоздать контейнер агента — окружение фиксируется при старте.
Значения заполненного `.env` в шаблон не переносятся автоматически, поэтому переменные агента
переносятся вручную:

```bash
grep -vE '^(ANTHROPIC_|LITELLM_|OLLAMA_)' .env > .env.claude
```

Новое окружение файл создаёт само: `make init-env` копирует `.env.claude.example` в `.env.claude`.
Откат — остановить сервис и удалить добавленные файлы; окружение агента возвращается правкой
`env_file` обратно на `.env`.
