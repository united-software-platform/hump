[![Ollama](https://img.shields.io/badge/Ollama-локальные%20модели-000000?logo=ollama&logoColor=white)](https://ollama.com/)

Hump — шлюз LLM-запросов: одна точка входа, за которой стоят и облачные модели, и модели,
выполняемые на собственной инфраструктуре. Системы обращаются к нему OpenAI-совместимым запросом,
называя маршрут, а не вендора; ключи, адреса провайдеров и учёт обращений остаются на стороне
шлюза. Разворачивается одной командой `make hump-up` и работает на `http://localhost:4000`.

## Предусловия

- **Docker с плагином Compose** на хосте — окружение поднимается целиком в контейнерах.
- **Ключ облачного провайдера** — нужен маршруту `hump-cloud`; без него работает только локальный
  маршрут.
- **Свободное место под веса модели** — около 1 ГБ для модели по умолчанию; первый запуск
  скачивает их в `data/ollama-models/`.
- **Пароль для базы** — придумать заранее, он задаётся в двух переменных окружения.

Локальная модель выполняется на процессоре: видеокарта не требуется, но и не используется.

## Развёртывание

```bash
git clone <адрес репозитория> hump
cd hump
make init-host
```

`make init-host` создаёт `.env` и `.env.claude` из примеров, каталоги `data/`, `.ssh/`
и `.claude-accounts/`, вносит их в `.gitignore` и генерирует SSH-ключ проекта. Существующие файлы
цель не перезаписывает — её можно вызывать повторно, в том числе после заполнения `.env`.

Конфигурацию SSH для git-хоста цель создаёт только при заполненной `GIT_HOST`; пока переменная
пуста, она об этом сообщает и файл не создаёт. Для работы шлюза это неважно — SSH нужен git-операциям
из контейнера агента.

Дальше — заполнить `.env` по разделу [Настройка](#настройка) и поднять окружение:

```bash
make hump-up
```

> **Примечание:** `make init` делает то же самое и дополнительно разворачивает инструменты SDD
> в контейнере агента. Для работы шлюза они не нужны — если Hump разворачивается как сервис,
> а не как среда разработки, достаточно `make init-host`.

## Настройка

Переменные шлюза живут в `.env`, созданном из [`.env.example`](./.env.example).

| Переменная | Назначение | Обязательна | Умолчание |
|------------|------------|-------------|-----------|
| `LITELLM_MASTER_KEY` | Административный ключ шлюза: им ходит проверка и им открывается панель, пока не заданы учётные данные UI. Обязан начинаться с `sk-` | да | нет |
| `POSTGRES_PASSWORD` | Пароль базы, в которой шлюз хранит своё состояние | да | нет |
| `DATABASE_URL` | Строка подключения шлюза к той же базе | да | `postgresql://litellm:@postgres:5432/litellm` |
| `ANTHROPIC_BASE_URL` | Адрес облачного провайдера маршрута `hump-cloud` | для `hump-cloud` | `https://api.deepseek.com/anthropic` |
| `ANTHROPIC_AUTH_TOKEN` | Ключ облачного провайдера | для `hump-cloud` | нет |
| `UI_USERNAME`, `UI_PASSWORD` | Вход в панель. Пока пусты, действует `admin` с паролем `LITELLM_MASTER_KEY` | нет | `admin` / нет |
| `POSTGRES_USER`, `POSTGRES_DB` | Имя пользователя и имя базы | нет | `litellm` |
| `LITELLM_SALT_KEY` | Шифрование ключей провайдеров, когда шлюз хранит их в базе | нет | нет |
| `LITELLM_PORT` | Порт шлюза на хосте | нет | `4000` |
| `OLLAMA_API_BASE` | Адрес сервера локальных моделей | нет | `http://ollama:11434` |
| `LITELLM_IMAGE`, `LITELLM_IMAGE_TAG` | Образ и тег шлюза | нет | `docker.litellm.ai/berriai/litellm` / `latest` |
| `POSTGRES_IMAGE`, `POSTGRES_IMAGE_TAG` | Образ и тег базы | нет | `postgres` / `17-alpine` |
| `OLLAMA_IMAGE`, `OLLAMA_IMAGE_TAG` | Образ и тег сервера моделей | нет | `ollama/ollama` / `latest` |

Два места требуют согласованных значений:

- пароль в `DATABASE_URL` совпадает с `POSTGRES_PASSWORD`, имя базы — с `POSTGRES_DB`; при
  расхождении шлюз не проходит авторизацию в базе при старте;
- тег образа шлюза стоит закрепить вместо `latest`: схему базы мигрирует сам образ при старте,
  и смена версии меняет схему уже заполненных данных.

За облачным маршрутом стоит не обязательно Anthropic: `anthropic` в конфигурации означает протокол,
а адрес сервиса задаёт `ANTHROPIC_BASE_URL` — подойдёт любой сервис с совместимым API.

> **Внимание:** ключи задаются только в `.env`, исключённом из репозитория.
> [`config/litellm.yaml`](./config/litellm.yaml) ссылается на имена переменных окружения
> и значений ключей не содержит.

### Окружение агента

Контейнер агента (`claude` из [`docker-compose.yml`](./docker-compose.yml)) читает отдельный файл
`.env.claude`, созданный из [`.env.claude.example`](./.env.claude.example). К работе шлюза он
отношения не имеет и нужен только тем, кто ведёт разработку через SDD kit.

| Переменная | Назначение |
|------------|------------|
| `SDD_KIT_IMAGE`, `SDD_KIT_IMAGE_TAG` | Образ и тег контейнера агента |
| `PROJECT_DIR`, `CLAUDE_CONFIG_DIR`, `CLAUDE_ACCOUNTS_DIR` | Пути внутри контейнера и каталог профилей аккаунтов |
| `SSH_DIR`, `SSH_KEY`, `SSH_CONFIG`, `SSH_KNOWN_HOSTS`, `CONTAINER_SSH_DIR` | Ключ и конфигурация SSH, пробрасываемые в контейнер |
| `GIT_HOST`, `GIT_USER`, `GH_TOKEN` | Git-хост, пользователь и токен для работы с репозиторием |
| `USER_ID`, `GROUP_ID` | Владелец файлов, создаваемых агентом в рабочем дереве |
| `AGENT_RUNNER_URL`, `AGENT_RUNNER_PORT`, `AGENT_RUNNER_TOKEN` | Подключение к [host-runner](./tools/host-runner) — через него агент запускает цели `make` на хосте |

Файлы разделены намеренно: имена `ANTHROPIC_*` зарезервированы самим Claude Code, и их попадание
в окружение агента отключает claude.ai-логин и коннекторы организации. Поэтому переменные продукта
Hump остаются в `.env` и в окружение агента не переносятся.

## Запуск

```bash
make hump-up
```

Поднимаются четыре сервиса из [`docker-compose.hump.yml`](./docker-compose.hump.yml):

| Сервис | Роль |
|--------|------|
| `postgres` | Хранилище состояния шлюза; стартует первым, остальные ждут его готовности |
| `litellm` | Сам шлюз; при старте мигрирует схему базы и публикует порт `4000` на хост |
| `ollama` | Сервер локальных моделей; порт наружу не публикует |
| `ollama-pull` | Разовая загрузка весов; при уже загруженной модели отрабатывает вхолостую |

Первый запуск дольше остальных: скачиваются образы и веса модели. Готовность видна по
`make hump-check` — до окончания миграций шлюз ещё не отвечает.

## Обращение к API

Шлюз принимает OpenAI-совместимые запросы на `http://localhost:4000`. Маршруты заданы
в [`config/litellm.yaml`](./config/litellm.yaml): `hump-local` — модель в Ollama, `hump-cloud` —
модель облачного провайдера.

```bash
curl http://localhost:4000/v1/chat/completions \
  -H "Authorization: Bearer sk-..." \
  -H "Content-Type: application/json" \
  -d '{"model":"hump-local","messages":[{"role":"user","content":"привет"}]}'
```

Для облачного маршрута меняется только имя модели — `hump-cloud`. Перечень доступных маршрутов
отдаёт `GET /v1/models` с тем же заголовком.

Ключ в заголовке — либо `LITELLM_MASTER_KEY`, либо ключ, выданный системе-потребителю в
[панели](#панель). Без действительного ключа шлюз отказывает и к провайдерам не обращается.

## Панель

Административная панель открывается по адресу `http://localhost:4000/ui`. Вход — значения
`UI_USERNAME` и `UI_PASSWORD` из `.env`; пока они не заполнены, действует пользователь `admin`
с паролем, равным `LITELLM_MASTER_KEY`.

> **Внимание:** вход мастер-ключом означает, что панель открывается тем же секретом, что и API
> моделей. Для окружения, доступного не только автору, `UI_USERNAME` и `UI_PASSWORD` задаются
> отдельными значениями.

Панель показывает настроенные маршруты, обращения к моделям и расход, а также выдаёт ключи доступа
отдельным системам-потребителям. Такой ключ работает наравне с мастер-ключом при обращении к API
моделей, но принадлежит одной системе: обращения по нему различимы в общем потоке, отзыв закрывает
доступ только этой системе, а управляющие маршруты шлюза такому ключу недоступны.

Порядок выдачи: в разделе ключей создать ключ, выбрать доступные ему маршруты и передать значение
системе-потребителю. Мастер-ключ остаётся административным и системам не раздаётся.

## Проверка

```bash
make hump-check
```

Цель читает ключи из `.env` и запускает [`tools/litellm/check.sh`](./tools/litellm/check.sh):
скрипт проверяет живость и готовность шлюза, подключение базы, состояние настроенных маршрутов
и отправляет по одному реальному запросу на каждый из них. Коды возврата: `0` — база подключена
и все маршруты отвечают, `1` — база не подключена или хотя бы один маршрут не ответил,
`2` — ошибка вызова или окружения.

Скрипт вызывается и напрямую — он сам выбирает доступный HTTP-клиент (`curl`, иначе `wget`),
а адрес шлюза берёт из `HUMP_GATEWAY_URL`:

```bash
HUMP_GATEWAY_URL=http://localhost:4000 LITELLM_MASTER_KEY=sk-... sh tools/litellm/check.sh
```

## Эксплуатация

| Задача | Как |
|--------|-----|
| Состояние и логи | `make hump-logs` |
| Остановить окружение | `make hump-down` |
| Сменить локальную модель | Имя правится в двух местах: маршрут `hump-local` в `config/litellm.yaml` и команда сервиса `ollama-pull` в `docker-compose.hump.yml`; значения должны совпадать |
| Увести локальный маршрут на внешний Ollama | Задать `OLLAMA_API_BASE` в `.env` |
| Закрепить версию шлюза | Задать `LITELLM_IMAGE_TAG` вместо `latest` |

Docker'а в контейнере агента нет, поэтому окружением он управляет целями `make` через
[host-runner](./tools/host-runner): разрешённые цели перечислены в его белом списке, а мастер-ключ
остаётся на хосте — цель `hump-check` читает `.env` сама.

## Данные шлюза

Данные сервисов лежат в каталоге `data/` внутри проекта, а не в томах Docker: их видно без
`docker volume`, можно скопировать и забрать в резервную копию обычными средствами.

| Каталог | Содержимое | Кто заполняет |
|---------|------------|---------------|
| `data/postgres/` | Состояние шлюза: выданные ключи и записи об обращениях | база, от имени пользователя `postgres` из образа |
| `data/ollama-models/` | Веса локальных моделей | сервис `ollama-pull` при запуске |

Каталог исключён из репозитория и создаётся целью `make init-host`. Содержимое переживает
`make hump-down` и пересоздание контейнеров.

> **Внимание:** потеря `data/postgres/` означает отзыв доступа у всех систем-потребителей сразу —
> выданные ключи восстановлению не подлежат. Резервное копирование в состав проекта не входит
> и остаётся обязанностью эксплуатации.

`data/postgres/` принадлежит пользователю базы из образа, а не владельцу репозитория: править его
содержимое напрямую не следует — этим занимается сама база. Записи об обращениях копятся,
и каталог растёт: автоматической ротации нет. Удалить накопленное можно только вместе с каталогом:

```bash
make hump-down
sudo rm -rf data/postgres
make hump-up
```

`sudo` нужен по той же причине — каталог создан не пользователем проекта. Следующий запуск
разворачивает базу заново, пустой и без выданных ключей.

## О проекте

### Почему «Сортировочная горка»

Сортировочная горка — железнодорожное сооружение для расформирования составов: поезд надвигают
на вершину насыпи, вагоны по одному скатываются вниз, и стрелки переводят каждый на тот путь,
который отвечает его назначению. Один входной путь, десятки выходных, решение принимается отдельно
по каждому вагону. Hump (англ. «горка») делает то же самое с запросами.

### Проблема и цель

Каждая система, которой нужна LLM, решает одни и те же вопросы заново: к какому провайдеру идти
и по какому протоколу, какую модель выбрать под задачу, что делать при отказе и исчерпании лимитов,
где держать ключи и как считать расход. Логика дублируется в Garden, Experience Mine и остальных
системах, смена модели требует правок в каждой, а единой картины расхода нет ни у кого.

Цель — снять выбор модели и провайдера с систем-потребителей: система формулирует, что ей нужно,
решение о маршруте принимает Hump.

### Задачи

- Принимать запросы по единому интерфейсу, не зависящему от провайдера.
- Выбирать модель и провайдера под каждый запрос: по типу задачи, требованиям к качеству, скорости
  и стоимости, по доступности и загрузке ресурсов.
- Поддерживать и облачные API, и локальные модели — включая сценарии, где данные не должны покидать
  собственную инфраструктуру.
- Переживать отказы провайдеров: повторять запрос и переключаться на запасной маршрут.
- Вести единый учёт обращений и расхода в разрезе систем и моделей.

## Состав

- [LiteLLM](https://www.litellm.ai/) — единый API-слой поверх LLM-провайдеров: приводит облачные
  сервисы разных вендоров к одному интерфейсу, поэтому Hump не зависит от протокола конкретного
  вендора. Он же даёт панель, учёт обращений и ключи систем-потребителей.
- [Ollama](https://ollama.com/) — запуск локальных моделей: направление, в котором запрос
  обрабатывается на собственной инфраструктуре, без обращения к внешним API.
- [PostgreSQL](https://www.postgresql.org/) — хранилище состояния шлюза: выданные ключи и записи
  об обращениях.

## Статус

Работает точка входа: запрос по OpenAI-совместимому API доходит и до локальной, и до облачной
модели. Работает панель: маршруты, обращения и расход видны, системам-потребителям выдаются
отдельные ключи.

Собственной логики маршрутизации у Hump пока нет — выбор маршрута делает система-потребитель,
называя имя модели, а распределение задаёт конфигурация LiteLLM. Перечисленные выше
[задачи](#задачи) — выбор модели по типу задачи, переключение на запасной маршрут при отказе,
единый учёт расхода — предмет следующих изменений.
