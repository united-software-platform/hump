Hump — интеллектуальный маршрутизатор LLM-запросов: единая точка входа, которая принимает запросы
от систем и распределяет их между доступными моделями и AI-провайдерами.

## Почему «Сортировочная горка»

Сортировочная горка — железнодорожное сооружение для расформирования составов. Прибывший поезд
надвигают на вершину насыпи, вагоны по одному скатываются вниз, и стрелки переводят каждый из них
на тот путь, который отвечает его назначению. Один входной путь, десятки выходных, и решение
принимается отдельно по каждому вагону.

Hump (англ. «горка») делает то же самое с запросами. Системы отправляют их в одну точку, а
маршрутизатор для каждого запроса выбирает, куда его направить: к какой модели и какому провайдеру —
исходя из типа задачи, требований запроса и доступных в этот момент ресурсов.

---

## Проблема

Каждая система, которой нужна LLM, решает одни и те же вопросы заново:

- к какому провайдеру идти и по какому протоколу — у облачных API и локальных моделей они разные;
- какую модель выбрать под конкретную задачу — дешёвую и быструю или тяжёлую и точную;
- что делать при недоступности провайдера, исчерпании лимитов и ошибках;
- где держать ключи доступа и как считать расход.

В результате одна и та же логика дублируется в Garden, Experience Mine и остальных системах, смена
модели или провайдера требует правок в каждой из них, а единой картины того, сколько запросов и куда
уходит, нет ни у кого.

---

## Цель

Снять выбор модели и провайдера с систем-потребителей. Система формулирует, что ей нужно, и
отправляет запрос в Hump; решение о маршруте принимает Hump.

---

## Задачи

- Принимать запросы по единому интерфейсу, не зависящему от конкретного провайдера.
- Выбирать модель и провайдера под каждый запрос: по типу задачи, требованиям к качеству, скорости
  и стоимости, а также по доступности и загрузке ресурсов.
- Поддерживать и облачные API, и локальные модели — в том числе сценарии, где данные не должны
  покидать собственную инфраструктуру.
- Переживать отказы провайдеров: повторять запрос и переключаться на запасной маршрут.
- Вести единый учёт обращений и расхода в разрезе систем и моделей.

---

## Состав

- [LiteLLM](https://www.litellm.ai/) — единый API-слой поверх LLM-провайдеров: приводит облачные
  сервисы разных вендоров к одному интерфейсу, поэтому Hump работает с ними единообразно и не
  зависит от протокола конкретного вендора.
- [Ollama](https://ollama.com/) — запуск локальных моделей: даёт маршрутизатору направление,
  в котором запрос обрабатывается на собственной инфраструктуре, без обращения к внешним API.

## Запуск шлюза

Окружение описано в [`docker-compose.hump.yml`](./docker-compose.hump.yml) и состоит из трёх
сервисов: `litellm` — сам шлюз, `ollama` — сервер локальных моделей, `ollama-pull` — разовая
загрузка весов при запуске. Маршруты заданы в [`config/litellm.yaml`](./config/litellm.yaml):
`hump-local` — модель в Ollama, `hump-cloud` — модель облачного провайдера.

Предусловия:

- Docker с плагином Compose на хосте;
- действующий ключ облачного провайдера;
- свободное место под веса модели — первый запуск скачивает их в том `ollama-models`.

Заполнить в `.env` переменные из блока `LiteLLM gateway` файла [`.env.example`](./.env.example):
`LITELLM_MASTER_KEY` (ключ доступа к шлюзу, начинается с `sk-`), а для облачного маршрута —
`ANTHROPIC_BASE_URL` и `ANTHROPIC_AUTH_TOKEN`.

За облачным маршрутом стоит не обязательно Anthropic: `anthropic` в конфигурации означает
протокол, а адрес сервиса задаёт `ANTHROPIC_BASE_URL` — подойдёт любой сервис с совместимым API.

Окружение агента (`claude`) живёт в отдельном файле `.env.claude`, созданном из
[`.env.claude.example`](./.env.claude.example): там только переменные агента. Имена `ANTHROPIC_*`
зарезервированы самим Claude Code, поэтому из `.env` их в окружение агента не переносят — иначе
отключается claude.ai-логин и коннекторы организации. Переменные продукта Hump остаются в `.env`.

Поднять окружение:

```bash
make hump-up
```

После запуска шлюз принимает OpenAI-совместимые запросы на `http://localhost:4000`, обращения
к API моделей требуют ключ `LITELLM_MASTER_KEY`. Состояние и логи — `make hump-logs`,
остановка — `make hump-down`.

Ollama работает на процессоре и порт наружу не публикует: к нему обращается только шлюз
по внутренней сети. Чтобы увести локальный маршрут на внешний Ollama, достаточно задать
`OLLAMA_API_BASE` в `.env`.

Смена локальной модели затрагивает два места: имя в `config/litellm.yaml` и команду сервиса
`ollama-pull` в `docker-compose.hump.yml` — значения должны совпадать.

> **Внимание:** ключи задаются только в `.env` — он исключён из репозитория. `config/litellm.yaml`
> ссылается на имена переменных окружения и значений ключей не содержит.

## Проверка

```bash
make hump-check
```

Цель читает ключи из `.env` и запускает [`tools/litellm/check.sh`](./tools/litellm/check.sh):
скрипт проверяет живость и готовность шлюза, состояние настроенных маршрутов и отправляет
по одному реальному запросу на каждый из них. Коды возврата: `0` — все маршруты отвечают,
`1` — хотя бы один не ответил, `2` — ошибка вызова или окружения.

Скрипт можно вызвать и напрямую — он сам выбирает доступный HTTP-клиент (`curl`, иначе `wget`),
а адрес шлюза берёт из `HUMP_GATEWAY_URL`:

```bash
HUMP_GATEWAY_URL=http://localhost:4000 LITELLM_MASTER_KEY=sk-... sh tools/litellm/check.sh
```

Docker'а в контейнере агента нет, поэтому окружением он управляет целями `make` через
[host-runner](./tools/host-runner): разрешённые цели перечислены в его белом списке, а мастер-ключ
остаётся на хосте — цель `hump-check` читает `.env` сама.

## Статус

Работает базовая точка входа: запрос по OpenAI-совместимому API доходит и до локальной, и до
облачной модели. Собственной логики маршрутизации Hump пока нет — выбор маршрута делает
система-потребитель, называя имя модели, а распределение задаёт конфигурация LiteLLM.

Задачи из одноимённого раздела — выбор модели по типу задачи и требованиям, переключение на
запасной маршрут при отказе, единый учёт расхода — предмет следующих изменений.
