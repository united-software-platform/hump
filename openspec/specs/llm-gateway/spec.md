## Purpose

Единая точка входа Hump для LLM-запросов: OpenAI-совместимый HTTP-API, за которым стоят маршруты
к локальной и к облачной модели, с проверкой работоспособности каждого маршрута, хранилищем
состояния, административной панелью и отдельными ключами доступа для систем-потребителей.

## Requirements

### Requirement: OpenAI-совместимая точка входа

Шлюз SHALL принимать запросы к моделям по OpenAI-совместимому HTTP-API на выделенном порту, чтобы
системы-потребители обращались к Hump тем же клиентом, что и к облачному провайдеру, и не зависели
от протокола конкретного вендора.

#### Scenario: Запрос на чат-дополнение по OpenAI-совместимому пути

- **WHEN** клиент отправляет `POST /v1/chat/completions` с именем модели из конфигурации шлюза
  и валидным ключом доступа
- **THEN** шлюз возвращает ответ в формате OpenAI Chat Completions с непустым содержимым ответа
  модели

#### Scenario: Перечень доступных моделей

- **WHEN** клиент запрашивает `GET /v1/models` с валидным ключом доступа
- **THEN** шлюз возвращает перечень настроенных имён моделей, включая локальный и облачный маршруты

### Requirement: Маршрут к локальной модели

Шлюз SHALL предоставлять маршрут к модели, выполняемой на собственной инфраструктуре, чтобы запрос
обрабатывался без обращения к внешним API.

#### Scenario: Запрос уходит на локальную модель

- **WHEN** клиент отправляет запрос с именем модели локального маршрута
- **THEN** шлюз обращается к локальному серверу моделей по адресу из конфигурации и возвращает его
  ответ, не обращаясь к внешним провайдерам

#### Scenario: Локальный сервер моделей недоступен

- **WHEN** локальный сервер моделей не отвечает по настроенному адресу
- **THEN** шлюз возвращает ошибку с указанием недоступного маршрута, а остальные маршруты остаются
  работоспособными

### Requirement: Маршрут к облачной модели

Шлюз SHALL предоставлять маршрут к модели облачного провайдера, а имя провайдера, имя модели
и ключ доступа SHALL задаваться конфигурацией и переменными окружения без правки кода.

#### Scenario: Запрос уходит на облачную модель

- **WHEN** клиент отправляет запрос с именем модели облачного маршрута
- **THEN** шлюз обращается к облачному провайдеру с ключом из окружения и возвращает его ответ

#### Scenario: Ключ облачного провайдера не задан

- **WHEN** шлюз запускается без заданного ключа облачного провайдера
- **THEN** облачный маршрут сообщает об ошибке доступа при обращении, а локальный маршрут
  продолжает обслуживать запросы

### Requirement: Контроль доступа к шлюзу

Шлюз SHALL отклонять обращения к API моделей без действительного ключа доступа, чтобы точка входа
не была открыта всем, кто видит порт.

#### Scenario: Запрос без ключа доступа

- **WHEN** клиент отправляет запрос к API моделей без ключа доступа или с недействительным ключом
- **THEN** шлюз отказывает в обслуживании и не обращается ни к одному провайдеру

### Requirement: Ключи доступа систем-потребителей

Шлюз SHALL выдавать отдельный ключ доступа каждой системе-потребителю, действующий наравне
с мастер-ключом при обращении к API моделей, чтобы обращения были различимы по потребителю,
а отзыв доступа одной системы не затрагивал остальные.

#### Scenario: Запрос по ключу системы-потребителя

- **WHEN** система-потребитель обращается к API моделей с выданным ей ключом
- **THEN** шлюз обслуживает запрос и связывает обращение с этой системой

#### Scenario: Отзыв ключа системы-потребителя

- **WHEN** ключ системы-потребителя отозван
- **THEN** обращения с этим ключом отклоняются, а обращения с остальными ключами продолжают
  обслуживаться

### Requirement: Секреты вне репозитория

Ключи доступа к шлюзу и к провайдерам SHALL передаваться через переменные окружения и не SHALL
храниться в файлах репозитория; файлы конфигурации SHALL ссылаться на переменные окружения,
а не содержать значения ключей.

#### Scenario: Конфигурация не содержит значений ключей

- **WHEN** файлы конфигурации шлюза попадают в репозиторий
- **THEN** они содержат только имена переменных окружения, а фактические значения ключей
  отсутствуют

### Requirement: Хранилище состояния шлюза

Шлюз SHALL хранить своё состояние — выданные ключи доступа и записи об обращениях — во внешнем
хранилище, и это состояние SHALL переживать перезапуск и пересоздание контейнера шлюза.

#### Scenario: Состояние переживает перезапуск

- **WHEN** шлюз перезапускается после выдачи ключа доступа системе-потребителю
- **THEN** выданный ключ продолжает действовать, а записи о прежних обращениях остаются доступны

#### Scenario: Хранилище недоступно при запуске

- **WHEN** шлюз запускается, а хранилище состояния не отвечает
- **THEN** проверка готовности сообщает, что хранилище не подключено, и вход в панель не выполняется

### Requirement: Административная панель

Шлюз SHALL предоставлять административную панель по HTTP, доступ к которой открывается только после
успешной аутентификации, чтобы состояние шлюза, его маршруты и обращения к моделям можно было
смотреть без чтения логов контейнера.

#### Scenario: Вход в панель

- **WHEN** пользователь открывает адрес панели и вводит действительные учётные данные
  администратора
- **THEN** панель открывается и показывает настроенные маршруты шлюза

#### Scenario: Вход с недействительными учётными данными

- **WHEN** пользователь вводит учётные данные, не совпадающие с заданными в окружении шлюза
- **THEN** панель отказывает во входе и не показывает ни маршрутов, ни ключей, ни данных обращений

#### Scenario: Учётные данные панели заданы окружением

- **WHEN** администратор задаёт имя пользователя и пароль панели переменными окружения
- **THEN** вход выполняется этими значениями, а значения по умолчанию перестают действовать

### Requirement: Проверка работоспособности

Шлюз SHALL предоставлять проверку состояния, различающую три уровня: процесс запущен и готов
принимать трафик; хранилище состояния подключено; каждый настроенный маршрут отвечает на реальный
запрос.

#### Scenario: Проверка живости и готовности

- **WHEN** выполняется проверка состояния запущенного шлюза
- **THEN** проверка подтверждает, что процесс жив и готов принимать трафик, без обращения
  к провайдерам

#### Scenario: Проверка подключения к хранилищу состояния

- **WHEN** выполняется проверка готовности шлюза
- **THEN** проверка сообщает, подключено хранилище состояния или нет, и завершается ошибкой, если
  хранилище не подключено

#### Scenario: Проверка маршрутов реальным запросом

- **WHEN** выполняется проверка настроенных маршрутов
- **THEN** проверка сообщает по каждому маршруту, отвечает он или нет, и завершается ошибкой, если
  хотя бы один из настроенных маршрутов не отвечает
